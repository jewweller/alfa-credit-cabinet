# ML-ранжирование ленты: модель, эксперимент, ограничения

Версия от 24.10.2026. Модель — `feed-logreg-1.0.0`. Как бэкенд вызывает модель и что ей передаёт —
[ml-ranking.md](ml-ranking.md); код — `ml/`, интеграция — `backend/app/services/feed.py`.

> **Главное.** Данные синтетические: реальных клиентов, кликов и данных банка в проекте нет и не
> будет (условия кейса). Результаты показывают, что модель восстанавливает **гипотезы о поведении
> клиентов, записанные в симуляторе**. Это не доказательство, что реальные клиенты будут читать
> ленту охотнее.

## 1. Цель

Упорядочить новости в персональной ленте (экраны C2, C8) лучше формулы правил из плана —
`3·ОКВЭД + 2·сегмент + 2·продукт + 3·статус + свежесть` (`backend/app/domain/feed_ranking.py`) — и
объяснить клиенту, почему он видит новость.

## 2. Что ранжируется и чего модель делать не может

- Кандидаты — новости из `seed/news.json`, **уже отобранные правилами**: отраслевые заметки —
  только своей отрасли, подсказки — только к текущему статусу заявки. В среднем около 5 на запрос.
- Модель только **переставляет** кандидатов. Бэкенд проверяет, что в ответе ровно те же новости,
  каждая один раз.
- Модель не участвует в скоринге, кредитном решении и подборе продукта (`rank_products` —
  заглушка: кандидатов 1–3).
- Модели не передаются ИНН, название компании и данные БКИ. Передаются: тип компании, ОКВЭД,
  регион, сегмент, дата регистрации, выручка ФНС по годам, статусы заявок клиента с кодом продукта
  и целью (`RankerProfile`, `backend/app/schemas/ml.py`).

## 3. Модель

**Логистическая регрессия** на 20 признаках (`ml/synth/features.py`): совпадения тегов, тема
новости, свежесть `exp(−дней/7)`, профиль клиента и пересечения (подсказка к шагу × от клиента
ждут действия, меры поддержки × микро/молодая компания, оборудование × рост выручки и др.).

- Оценка: `z = b + Σ wⱼ·xⱼ`, `score = σ(z)`; порядок — по `z`, при равенстве — по `id`.
- Параметры: `ml/models/feed_logreg.json` (20 коэффициентов, свободный член, `C`, хеши данных,
  метрики на отложенной части).
- Работа модели — только стандартная библиотека Python: `numpy`, `scikit-learn`, `xgboost` не
  нужны. В образе API вызов занимает доли миллисекунды (проверено: первый вызов с загрузкой весов —
  0,4 мс).

**Почему не XGBoost.** ML-команда сравнила с `XGBRanker` (ветка `feat/ml-stub`, PR #27; отчёты — `ml/reports/` в ней):
выигрыш +0,004 NDCG@5, на аддитивном сценарии — проигрыш, а в продукте нужны `numpy`,
`xgboost`, `scikit-learn` и прогрев около 2 с. Эти цифры XGBoost заявлены ML-командой; бэкенд их
не перепроверял (без `xgboost` не запустить).

## 4. Обучение

| | |
| --- | --- |
| Генерация запросов | `ml/synth/make_requests.py` (ML-команда, ветка `feat/ml-stub`, PR #27): seed 42, 4000 клиентов × 3 визита, кандидаты отбираются кодом бэкенда (`eligible_news`) |
| Клики | `ml/synth/simulate.py` (ML-команда): seed 142, сценарий `mixed`; клик — бросок монетки со скрытой вероятностью интереса |
| Разбиение | по клиентам 70/15/15 % (train/validation/test) |
| Метод | `ml/synth/logreg.py`: метод Ньютона, целевая функция как у `sklearn` — `C·Σ logloss + ½‖w‖²`, свободный член без штрафа; чистый Python |
| Выбор `C` | `C ∈ {0,1; 1; 10}` по NDCG@5 на validation: 0,47733 / **0,47759** / 0,47750 → `C = 1` |

**Совпадение с ML-командой.** Хеши сгенерированных данных совпадают с метаданными ветки `feat/ml-stub` (PR #27) — данные
те же. На тестовой части seed 42 метрики практически совпадают с отчётом ML-команды
(NDCG@5 логистической регрессии 0,4859 у нас и 0,4858 у них, правил — 0,3967 у обоих). Их
`logistic.json` (обучен `sklearn` на float32) не доведён до минимума целевой функции (значение
199 831,45 против 199 828,30 у нас при `C = 10`); порядок новостей с ним совпадает в 95,4 %
запросов. В продукте — наши веса: они воспроизводятся тестом
`backend/tests/unit/test_ml_ranking.py::test_published_weights_are_reproduced_by_training`
(переобучение даёт те же коэффициенты с точностью 1e-9).

**Замечания к признакам** (для ML-команды): `m_okved` всегда совпадает с `topic_industry`,
`m_product` — с `product_known`, а `product_topic_x_no_apps` в данных всегда 0. Эффективно признаков
17; на качество это не влияет (L2 делит вес поровну), но признаки стоит почистить.

## 5. Результаты

Метрика — NDCG@k по кликам (линейный gain, запрос без кликов = 0) и oracle NDCG@5 — совпадение
со скрытым порядком симулятора. Порядок правил — как в `rank_news`: вес, затем свежие, затем `id`.

### 5.1. Новые синтетические клиенты, которых модель не видела

Три seed (101, 202, 303), по 4000 клиентов × 3 визита, клики — seed + 1000, сценарий `mixed`;
считаются все 12 000 запросов каждого seed.

| Порядок | NDCG@3 | NDCG@5 | Oracle NDCG@5 |
| --- | ---: | ---: | ---: |
| оракул (знает скрытые вероятности) | 0,434 | **0,481** | 1,000 |
| **логистическая регрессия** | 0,427 | **0,475** | 0,986 |
| правила бэкенда | 0,320 | **0,394** | 0,843 |
| случайный порядок | 0,305 | **0,382** | 0,829 |

По seed NDCG@5 модели: 0,4808 / 0,4723 / 0,4720; правил: 0,3989 / 0,3907 / 0,3935.

### 5.2. Отложенная часть seed 42 (1800 запросов)

| Порядок | NDCG@5 | Oracle NDCG@5 |
| --- | ---: | ---: |
| оракул | 0,4876 | 1,0000 |
| логистическая регрессия | 0,4859 | 0,9867 |
| правила | 0,3967 | 0,8428 |
| случайный | 0,3859 | 0,8320 |

### 5.3. Как читать NDCG@5 ≈ 0,48

- Около **36 % запросов без единого клика**, им ставится 0 — максимум метрики около 0,64.
- Клики случайны: даже оракул набирает **0,481** — это реальный потолок.
- Кандидатов около 5, NDCG@5 почти всегда покрывает весь список; случайный порядок даёт 0,38.

Доля достижимого (0 % — случайный порядок, 100 % — оракул): модель ≈ **94 %**, правила ≈ **12 %**.

## 6. Причины «Почему вы это видите»

Модель возвращает для новости до двух причин — совпавшие теги новости с **наибольшим
положительным вкладом** `wⱼ·xⱼ` в оценку. Вклад линейной модели считается точно, поэтому причина —
честное «почему модель подняла эту новость». Коды и тексты:

| Признак | Код | Текст |
| --- | --- | --- |
| `m_okved` | `okved` | «Новость вашей отрасли (ОКВЭД 10.71)» |
| `m_status` | `status` | «Подсказка к текущему этапу вашей заявки» |
| `m_product` | `product` | «Связано с продуктом из вашей заявки» |
| `m_segment` | `segment` | «Подобрано для микробизнеса» / «…для малого бизнеса» |

- Тексты без персональных данных: только ОКВЭД и сегмент, которые лента правил и так показывает.
- Свежесть и пересечения не имеют своего кода в контракте (`FeedReasonCode`), поэтому в причины не
  попадают, хотя влияют на порядок сильнее всего.
- У «общих» новостей вклад отрицательный — модель причин не даёт, показываются причины правил
  («Полезно всем клиентам»).
- Стоимость: несколько умножений на новость, отдельной модели для объяснений нет.

Бэкенд дополнительно проверяет каждую причину (`_model_reasons`): текст не пустой, код совпадает
с реальным совпадением новости по правилам. Иначе — причины правил.

## 7. Поведение в продукте

- `ML_RANKING_ENABLED=true` по умолчанию в `docker-compose.yml` и `.env.example`; в коде по
  умолчанию `false` (тесты и запуск вне Docker). Таймаут — `ML_TIMEOUT_SEC` (1 с).
- `GET /feed` → `ranking.method = ml`, `ranking.model_version = feed-logreg-1.0.0`.
- **Возврат к правилам** (порядок и причины правил, `method = rules`, предупреждение в лог), если
  модель бросила исключение (в том числе повреждённый файл весов), не ответила за 1 с, вернула ответ
  не по схеме, не тех или повторяющихся кандидатов, не указала версию.
- Тесты: `backend/tests/unit/test_ml_ranking.py` (модель) и
  `backend/tests/api/test_feed_api.py`, раздел «Ранжирование моделью ML» (интеграция).

## 8. Как воспроизвести

Из корня репозитория, окружение бэкенда (`backend/.venv`):

```bash
# обучение: генерирует данные seed 42 в ml/data/, если их нет, и пишет веса
PYTHONPATH=.:backend backend/.venv/bin/python -m ml.synth.logreg \
    --data ml/data/seed-42 --out ml/models/feed_logreg.json
# проверка, что веса воспроизводятся
cd backend && .venv/bin/pytest -q tests/unit/test_ml_ranking.py
```

Оценка на новых seed (раздел 5.1): `make_requests.generate(seed=s)`, `simulate(seed=s+1000,
"mixed")`, затем `logreg.load` и `logreg.evaluate` по всем запросам.

## 9. Ограничения и риски

- **Синтетика с гипотезами авторов.** Правила проигрывают в том числе потому, что не содержат
  гипотез симулятора (свежесть, подсказки к шагу при ожидании действия). «Модель лучше правил» —
  вывод про симулятор, не про реальных клиентов; на проде шаги нужно повторить на реальных кликах.
- **Маленький каталог:** 28 новостей и около 5 кандидатов на запрос.
- **Около трети обучающих групп** с одинаковыми метками ничего не дают ранжированию.
- **Различие весов с `feat/ml-stub` (PR #27)** — см. раздел 4; на порядок новостей влияет в 4,6 % запросов.
- **Тексты причин** — шаблоны по коду тега; бэкенд проверяет код и длину, но не формулировку.

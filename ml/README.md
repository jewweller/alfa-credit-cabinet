# ML-ранжирование персональной ленты

В продуктовой версии `main` новости ранжирует **логистическая регрессия
`feed-logreg-1.0.0`**. Мы сравнили её подход с XGBoost LambdaMART и выбрали для
API логрег: небольшой прирост качества XGBoost на синтетике не оправдывает тяжёлые
зависимости и отдельный прогрев модели.

Интеграция логрега выполнена в [PR #29](https://github.com/jewweller/alfa-credit-cabinet/pull/29).
XGBoost, обучение и отчёты экспериментов сохранены в ветке `feat/ml-stub`,
[коммит `8f171f1`](https://github.com/jewweller/alfa-credit-cabinet/tree/8f171f10889878c91e994f806088db7fd2f8b5e9/ml).
В этой исследовательской ветке `rank_feed` по-прежнему вызывает XGBoost;
продуктовый вызов описан для `main`.

## Задача и границы модели

Бэкенд сначала отбирает допустимые новости по профилю компании и статусам заявок.
Модель получает этот список и меняет только порядок: все новости возвращаются ровно
по одному разу. При ошибке или таймауте бэкенд использует порядок правил.

Модель не участвует в кредитном скоринге и решениях по заявкам. Подбор продуктов
`rank_products` сохраняет порядок бэкенда. ИНН, название компании и данные БКИ
модели не передаются.

## Данные и признаки

Реальных кликов и данных банка в эксперименте нет. Запросы и клики синтетические:

- каталог — 28 новостей из `seed/news.json`;
- запросы создаются в точном формате `FeedRankRequest` и проверяются схемой бэкенда;
- кандидатов отбирает существующая функция бэкенда `eligible_news`;
- клик разыгрывается по вероятности интереса из симулятора;
- идентификаторы клиентов/запросов и метки хранятся отдельно от входного JSON;
- обучающая, проверочная и тестовая части разделены по клиентам в пропорции 70/15/15;
- все посещения одного клиента принадлежат одной части выборки.

На независимой проверочной выборке в среднем **5,24 кандидата и 1,07 клика на запрос**,
положительными являются 20,4% меток. `click=0` означает отсутствие смоделированного
клика; это не однозначное утверждение, что новость клиенту не подходит.

Обе модели используют одинаковые 20 признаков: совпадения тегов, тему новости,
свежесть, характеристики компании и взаимодействия, например «подсказка по шагу ×
от клиента ждут действия» и «оборудование × рост выручки». Расчёт общих признаков,
генератор, симулятор и [описание данных](DATA_CARD.md) перенесены из исследования в `main`.
Хеши обучающих данных совпадают.

В текущем каталоге есть избыточность: `m_okved` совпадает с `topic_industry`,
`m_product` — с `product_known`, а `product_topic_x_no_apps` всегда равен нулю.
Количество объявленных признаков поэтому не равно количеству независимых сигналов.

## Честное сравнение моделей

Ниже результаты **одного исследования на одной независимой выборке**:
seed 20261024, 4000 новых синтетических клиентов, три запроса на каждого — всего
12 000 запросов. Метки кликов созданы с seed 20261124, сценарий `mixed`.
Выборка сформирована после фиксации настроек XGBoost и не использовалась для их выбора.

Основная метрика — NDCG@5 по кликам, среднее по запросам. Если кликов нет,
метрика запроса равна нулю. Столбец «есть клик» — отдельная диагностика только
по запросам с положительной меткой; он не заменяет основную метрику.

| Порядок новостей | NDCG@5, все запросы | NDCG@5, есть клик |
| --- | ---: | ---: |
| Правила бэкенда | 0,39357 | 0,61955 |
| Логрег исследования, `sklearn`, `C=10` | 0,47445 | 0,74687 |
| XGBoost до расширенного подбора | 0,47698 | 0,75085 |
| **XGBoost после подбора** | **0,47850** | **0,75325** |
| Диагностика: порядок по скрытой вероятности интереса | 0,48109 | 0,75733 |

**Не следует смешивать эту таблицу с оценкой продуктового логрега.** В `main`
логрег переобучен методом Ньютона на чистом Python и выбран `C=1`; это другие веса,
а не копия исследовательского `models/logistic.json`. На трёх новых seed
101/202/303 продуктовая модель получила средний NDCG@5 около **0,475**, правила —
**0,394**. Эти числа получены на другой выборке и не образуют прямого сравнения
с XGBoost из таблицы выше. Методика и результаты продуктовой модели описаны в
[документе эксперимента `main`](https://github.com/jewweller/alfa-credit-cabinet/blob/fc71208ffdb62391df2190c4e5de4bc06fd51ee5/docs/ml-experiment.md).

### Что дал подбор XGBoost

Проверены 33 конфигурации. Шесть лучших и исходная перепроверены на validation
seed 43 и 44; итоговый выбор сделан по среднему validation NDCG@5 seed 42/43/44.
Признаки, симулятор и исходные обучающие данные при подборе не менялись.

Выбраны `rank:ndcg`, глубина 2, `learning_rate=0.15`, `min_child_weight=20`,
`reg_lambda=30`, `reg_alpha=0.1`, `subsample=0.7`, `colsample_bytree=0.8`,
стратегия пар `topk=5`; early stopping оставил 216 используемых деревьев.

На независимой выборке прирост настроенного XGBoost составил:

| Сравнение | Разница NDCG@5 | 95% доверительный интервал |
| --- | ---: | ---: |
| XGBoost − логрег исследования | +0,00405 | [0,00242; 0,00600] |
| XGBoost − исходный XGBoost | +0,00152 | [−0,00001; 0,00296] |
| XGBoost − правила | +0,08493 | [0,08051; 0,08970] |

Интервалы рассчитаны парным bootstrap по клиентам, 1000 повторов. Выигрыш относительно
исследовательского логрега подтверждается **в этом синтетическом эксперименте**, но
составляет около 0,85% относительно его NDCG@5. Прирост относительно исходного XGBoost
статистически не подтверждён на уровне этих интервалов.

В первоначальном сравнении на seed 42/43/44 интервалы разницы XGBoost и логрега
включали ноль. На дополнительном аддитивном сценарии логрег был лучше:
NDCG@5 **0,44800 против 0,44289** у XGBoost. Преимущество метода зависит от того,
какие поведенческие гипотезы заложены в синтетику.

### Почему NDCG@5 около 0,48 не означает «48% точности»

В независимой выборке **4377 из 12 000 запросов (36,5%) не имеют кликов** и получают
нулевую оценку. Даже идеальная сортировка уже известных кликов дала бы максимум
**0,63525** при таком правиле подсчёта.

Кроме того, клики случайны: порядок по скрытым вероятностям интереса даёт 0,48109.
Это диагностический ориентир, а не строгий верхний предел результата на конкретной
реализации случайных кликов. Он показывает, почему идеального совпадения с метками
не стоит ожидать даже при знании симулятора.

## Почему в API выбран логрег

| Критерий | Логрег в `main` | XGBoost в исследовании |
| --- | --- | --- |
| Работа модели | Стандартная библиотека Python | NumPy, XGBoost, scikit-learn и транзитивные зависимости |
| Веса | 20 коэффициентов и свободный член в JSON | Деревья в `.ubj` |
| Первый вызов | Не требует отдельного прогрева для бюджета 1 с | Около 2,1 с с импортом библиотек на тестовом Mac |
| После прогрева | Несколько скалярных операций на признак | p95 около 0,24 мс на 15 кандидатов на тестовом Mac |
| Причины показа | До двух совпавших тегов с положительным вкладом в оценку | В исследовательском ответе причины пустые; используются причины правил |
| Подключение | Интегрирован в API в PR #29 | Нужны установка зависимостей, прогрев и проверка образа API |

Измерения времени зависят от окружения и методики. Для продуктового логрега бэкенд
зафиксировал первый вызов с чтением весов около 0,4 мс в образе API; локальная проверка
с импортом пакета без сторонних библиотек заняла около 5 мс. Это разные измерения.

**Инженерный выбор:** существенный выигрыш относительно правил уже обеспечивает
логрег. Дополнительные +0,004 NDCG@5 исследовательского XGBoost на синтетике не
компенсируют усложнение поставки и запуска для текущего демонстрационного сервиса.
XGBoost сохраняется как исследование и вариант для дальнейшего сравнения на реальных показах.

## Как устроена продуктовая версия

Код и артефакты ниже относятся к `main`:

| Файл | Назначение |
| --- | --- |
| `ml/synth/ranking.py` | `rank_feed`, расчёт оценок и причин показа на стандартной библиотеке |
| `ml/synth/features.py` | Общий расчёт 20 признаков |
| `ml/synth/logreg.py` | Обучение и оценка методом Ньютона на чистом Python |
| `ml/models/feed_logreg.json` | Веса `feed-logreg-1.0.0`, параметры обучения и хеши данных |
| `backend/app/services/feed.py` | Вызов модели, таймаут и возврат к правилам |

При успешном вызове `GET /feed` возвращает `ranking.method = ml` и
`ranking.model_version = feed-logreg-1.0.0`. В Docker и `.env.example`
`ML_RANKING_ENABLED=true` по умолчанию; в настройках Python без переменной окружения —
`false`. Бэкенд возвращается к правилам при исключении, таймауте 1 с, некорректной схеме,
чужих/повторяющихся кандидатах или пустой версии модели. Проверка причин показа
оставляет только непустые объяснения с реально совпавшими кодами тегов.

Устанавливать зависимости XGBoost и вызывать `warmup()` для продуктового логрега не нужно.

- [Замеры запуска и задержки XGBoost](https://github.com/jewweller/alfa-credit-cabinet/blob/8f171f10889878c91e994f806088db7fd2f8b5e9/ml/reports/latency.json).
- [Продуктовый эксперимент и воспроизведение логрега](https://github.com/jewweller/alfa-credit-cabinet/blob/fc71208ffdb62391df2190c4e5de4bc06fd51ee5/docs/ml-experiment.md).

В исследовательской ветке `feat/ml-stub` из каталога `ml/` можно воспроизвести
уже выбранную XGBoost-модель без нового подбора по проверочной выборке:

```bash
./run.sh python -m ml.synth.tune --reproduce
```

Нужны Python 3.12, `uv` и системная библиотека OpenMP; на macOS для XGBoost может
потребоваться `brew install libomp`. Зависимости Python закреплены в `uv.lock`.
Команда проверяет хеши данных, переобучает выбранную модель и сверяет предсказания.
Она не является командой установки продуктовой модели в API.

## Ограничения

Результаты относятся к синтетическому симулятору и текущему каталогу, а не доказывают
рост CTR реальных клиентов. Совпадение формата запросов обеспечивает техническую
совместимость, но не совпадение распределений с будущими данными. Модель не анализирует
текст новости, не проверялась на новых текстах и не моделирует смещение кликов по позиции.
Перед использованием на реальных показах потребуются новая оценка и переобучение.

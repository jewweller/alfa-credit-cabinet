# Синтетические данные для ранжирования кредитов

Модуль моделирует компании, запросы, конфигурации кредита, показ и воронку клиента.
`XGBRanker` ранжирует предложения; кредитное решение остаётся набором правил.
Все записи вымышлены. Модель по умолчанию **не подключается к продукту**.

Готовые результаты: [пример Parquet](examples/README.md),
[отчёт по трём seed на полном объёме](reports/README.md),
[модель и список признаков](models/README.md).

## Быстрый запуск

Python 3.12, [uv](https://docs.astral.sh/uv/), для теста паритета — Node.js 24.
Все команды выполняются из корня репозитория:

```sh
uv sync --project ml --frozen
uv run --project ml python -m ml.synth \
  --config ml/synth/config.yaml --seed 42 --out data/ --debug
```

`--debug` создаёт 1% компаний: 200 вместо 20 000. `--companies 1000` задаёт
явный объём. Без этих флагов получается около 60 000 запросов, 1–5 на компанию.
Число кандидатов зависит от лимитов; максимум 20 на запрос. Обычно их больше
10, поэтому полный набор может быть больше стартовой оценки 600 000 строк из ТЗ.

Последняя строка вывода — каталог `data/synth-v0.1.0-seed42-<config-hash>/`.
Существующий набор не перезаписывается; для повторной проверки выберите другой
`--out`. Вывод сначала пишется во временный каталог и публикуется переименованием
после успешного завершения. Незавершённые собственные файлы удаляются при ошибке.

С активированным окружением работает и команда из ТЗ:

```sh
source ml/.venv/bin/activate
python -m ml.synth --config ml/synth/config.yaml --seed 42 --out data/
```

## Файлы набора

| Файл | Содержимое |
|---|---|
| `companies.parquet` | Компании, корректные уникальные ИНН, вымышленные имена |
| `fns_profiles.parquet`, `bki_reports.parquet` | Снимки источников на каждый запрос с `request_id`, `company_id`, `as_of` |
| `requests.parquet` | Все запросы, включая пустые и исключённые, причины исключения, политика показа |
| `candidates.parquet` | Конфигурации в лимитах, ставки, платежи, позиция показа |
| `outcomes.parquet` | Контрфактическое решение правил, фактическая воронка, финальный исход, метка |
| `latent_truth.parquet` | Скрытые свойства и ожидаемая полезность; **только оценка** |
| `evaluation.parquet` | Все кандидаты, признаки, идентификаторы для аудита, экспозиция, split |
| `train.parquet`, `validation.parquet`, `test.parquet` | Только `qid`, `label` и 34 разрешённых признака |
| `features.json` | Порядок признаков и полный фиксированный словарь категорий |
| `config.json`, `manifest.json` | Разрешённая конфигурация, seed, версии, хеши файлов и исходников |
| `quality.json`, `DATA_CARD.md` | Фактические распределения, гистограммы, воронка и открытые проверки |

`qid` равен UUID запроса. Строки отсортированы по `qid`, внутри группы — по позиции
показа. Перед передачей в XGBoost UUID преобразуется в монотонный целочисленный
код группы. Идентификаторы, позиции, исходы и скрытые свойства не входят в `X`.
Деньги в журналах — строки `"3000000.00"`, в матрице признаков — `float32`.
Категории хранятся в Parquet как dictionary и восстанавливаются в pandas `category`.

## Обучение и отчёт

Подставьте путь, напечатанный генератором:

```sh
uv run --project ml python -m ml.synth.train \
  --data data/synth-v0.1.0-seed42-<config-hash> --out ml/runs/seed42
```

Сохраняются `ranker-0.1.0.json`, `features.json`, `report.json`. Есть проверка
сохранения/загрузки модели с точным совпадением предсказаний. По умолчанию
используются параметры ТЗ, early stopping по `ndcg@3` на validation.
`MAP@3` считается в отчёте после преобразования релевантности в `label > 0`:
в закреплённом XGBoost 3.0.2 встроенная MAP не принимает метки 0–4.

```sh
uv run --project ml python -m ml.synth.experiment \
  --seeds 42 43 44 --companies 2000 --out ml/runs/experiment
```

`REPORT.md` и `summary.json` содержат NDCG@3/@5, среднее и стандартное отклонение
по seed, бейзлайны A/B/C, идеальную политику, важность признаков, срезы по регионам
и сегментам. Контрольные модели обучаются только на свойствах кандидата и на
перемешанных внутри группы метках. `--estimators 30` — быстрый технический прогон;
`--no-ablations` у `train` отключает контрольные модели.

Оценки разделены на:

- `observed_positive_queries`: показанные варианты в запросах с позитивами;
- `observed_all_shown`: все показанные варианты, включая нулевые группы
  (для них NDCG определён как 0);
- `oracle_all_candidates`: все прошедшие фильтр варианты против линейной
  ожидаемой полезности из `latent_truth`. Группы с нулевой полезностью всех
  вариантов не имеют идеального порядка и исключаются из этой метрики
  (их число явно указано). Идеальная политика на остальных имеет NDCG=1.

Идеальный порядок не обязан максимизировать случайные наблюдаемые клики.
Среднее по seed не заменяет проверку качества на реальных данных.

## Позиционное смещение

20% запросов получают случайный порядок; журнал содержит позицию и политику.
При обучении используются только показанные варианты, включая в случайной доле.
Непоказанным в случайной доле записывается 0 в журнале, в остальных — `null`.
Они не выдаются за наблюдавшиеся позиции в обучении.

`train --unbiased` включает экспериментальный `lambdarank_unbiased=True`.
В XGBoost 3.0.2 отдельного параметра с массивом позиций нет: порядок строк внутри
`qid` должен соответствовать показу. Он сохраняется в наших файлах.
Это метод для кликов; перенос на градуированные метки воронки требует отдельной
проверки, поэтому он выключен по умолчанию. Позиция никогда не является признаком.
Построчные IPS-веса в `sample_weight` **не** передаются: `XGBRanker` ожидает
один вес на группу, а не на строку.

Документация: [Learning to Rank](https://xgboost.readthedocs.io/en/release_3.0.0/tutorials/learning_to_rank.html),
[Python API](https://xgboost.readthedocs.io/en/release_3.0.0/python/python_api.html).

## Интеграция с продуктом

Проверенные источники и неоднозначности перечислены в [DATA_CARD.md](DATA_CARD.md).
В `main` на момент начала работы был только план; актуальные API и моки изучены
в `be/skeleton` и `fe/client-cabinet`. Их изменения не переносятся этим модулем.
Рабочих `backend/app/scoring/engine.py`, `backend/app/decision/engine.py` и
`POST /products/recommend` в проверенных ветках ещё нет.

`ml.synth.rules.RuleEngine` — граница интеграции. Когда появятся backend-движки:

1. Реализовать адаптер с `score(...) -> Score` и `decide(...) -> Decision`,
   который **импортирует** рабочие функции скоринга и решения.
2. Указать его в `rules.adapter: package.module:AdapterClass` и обновить
   `rules.version`. Конструктор получает конфигурацию.
3. Прогнать демо- и граничные тесты. Если backend-движки уже присутствуют в дереве,
   генератор откажется молча использовать эталонную реализацию плана.
4. В API передавать снимки на момент запроса в `build_features` или
   `build_feature_rows`. Это те же функции, что использует генератор.
5. Подключить `rank_candidates(..., enabled=settings.RANKER_ENABLED,
   model_directory=...)`; значение флага по умолчанию — `false`.
   При отключении или недоступном/несовместимом артефакте используется бейзлайн B.
   API должен до ранжирования применить жёсткие ограничения и журналировать fallback.

Адаптер ранжирования не изменяет кредитное решение. Сначала необходимо завершить
Must-функции и согласовать порог внедрения и оставшиеся вопросы ТЗ.

## Тесты

```sh
uv run --project ml ruff check ml
uv run --project ml ruff format --check ml
uv run --project ml python -m pytest -c ml/pyproject.toml ml/synth/tests
```

CI запускает те же проверки: демо, границы правил, соответствие API, паритет
аннуитета на 203 примерах с исходным TypeScript, ИНН, отсутствие утечек,
разбиение, воронка, воспроизводимость между процессами, распределения на 10 000
компаниях, обучение с абляциями и восстановление модели. Без Node локально
пропускается только тест межъязыкового паритета; в CI Node устанавливается.

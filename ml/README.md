# ML-ранжирование ленты

Основная модель — `XGBRanker` (LambdaMART, `rank:ndcg`); обучаемый бейзлайн —
`LogisticRegression`. Дополнительно сравниваем с правилами бэкенда и случайным порядком.
Модель упорядочивает уже отобранные новости, возвращает всех кандидатов ровно по одному.
`rank_products` сохраняет порядок бэкенда. Кредитных решений модель не принимает.

Все новые файлы, зависимости, данные и отчёты находятся внутри `ml/`.
Код бэкенда используется только для чтения: его схемы проверяют запросы,
его `eligible_news` отбирает кандидатов для синтетики.

## Запуск

Нужны Python 3.12 и `uv`. Команды из `ml/`:

```bash
./run.sh python -m ml.synth.experiment
./run.sh pytest -q --basetemp=runs/pytest-temp
./run.sh python -m ml.synth.benchmark
./run.sh ruff check .
./run.sh ruff format --check .
```

`run.sh` устанавливает зависимости по `uv.lock`, сохраняет окружение и кеш внутри `ml/`,
задаёт пути импортов и отключает запись `.pyc`, в том числе в читаемые папки бэкенда.
Исходный эксперимент (до подбора параметров): seed 42, 43, 44; 4000 клиентов × 3 запроса на seed;
дополнительно аддитивный сценарий на seed 42. Настройки можно изменить:

```bash
./run.sh python -m ml.synth.experiment --clients 4000 --visits 3 --seeds 42 43 44
```

Повторный запуск перезаписывает соответствующие `ml/data`, `ml/runs`, `ml/models`
и отчёт. Публикуется первый заранее выбранный seed, а не лучший по тесту.

По отдельным этапам:

```bash
./run.sh python -m ml.synth.make_requests --out data/seed-42 --clients 4000 --visits 3 --seed 42
./run.sh python -m ml.synth.simulate --data data/seed-42 --seed 142 --scenario mixed
./run.sh python -m ml.synth.train --data data/seed-42 --out runs/seed-42 --seed 42
```

Последняя команда сохраняет эксперимент в `runs`; публикацию в `models` выполняет
полный `experiment`, чтобы веса, метаданные и результаты относились к одному запуску.

## Формат данных

`data/seed-*/requests.jsonl`: одна строка — **точный JSON `FeedRankRequest`**:
`now`, `profile`, `candidates`. Все поля, типы, допустимые значения и вложенность
проверяются существующей схемой `backend/app/schemas/ml.py`. Генератор сохраняет
исходные новости из `seed/news.json` и вызывает `eligible_news`.
На вход рабочего `rank_feed` приходит такой же объект. Тексты и ID не являются признаками.

Обучающие дополнения хранятся отдельно:

- `metadata.jsonl`: `request_id` (номер строки запроса, с нуля), `client_id`, `split`;
- `clicks.csv`: `request_id`, `candidate_id`, `click`, `p_interest`;
- `generation.json`, `simulation.json`: параметры воспроизведения.

`request_id` задаёт группу кандидатов для XGBoost (`qid`). Все строки группы находятся
рядом. `client_id` используется только для разделения выборок и доверительных интервалов.
`p_interest` — скрытая вероятность из симулятора, только для отдельной oracle-оценки.
Ни ID, ни метки, ни `p_interest` в матрицу признаков не входят.
Модель учится только на `click`, причём симулятор считает показанными всех кандидатов.

## Признаки

Общие для обучения и рабочего вызова 20 признаков из шага 3 исходного how-to:

| Группа | Признаки |
|---|---|
| Совпадения | `m_okved`, `m_status`, `m_product`, `m_segment`, `m_general` |
| Тема | `topic_product`, `topic_industry`, `topic_step`, `topic_support` |
| Свежесть | `fresh_7d` |
| Профиль и связь с продуктом | `micro`, `young`, `no_apps`, `action_needed`, `product_known`, `growth` |
| Пересечения | `step_x_action`, `support_x_small_or_young`, `product_topic_x_no_apps`, `equipment_x_growth` |

Расчёт — `synth/features.py`. Пустая/нулевая предыдущая выручка даёт рост 0,
рост ограничен диапазоном −1…1. Молодая компания — младше двух лет.
Свежесть — `exp(-max(age_days, 0) / 7)`. Наивные datetime интерпретируются как UTC.
`rule_score` используется только как отдельный бейзлайн, не как обучающий признак.
Названия и порядок признаков, версия расчёта и SHA-256 весов проверяются при загрузке.

## Обучение и оценка

70/15/15% **клиентов**, с воспроизводимым разбиением; запросы одного клиента не пересекают
части. Генератор создаёт независимые сценарии заявок в разные посещения; они не являются
историей реальных переходов статусов. Профиль компании и выручка между посещениями сохраняются.

LogReg: `C ∈ {0.1, 1, 10}`. XGBoost: три фиксированных набора глубины/регуляризации,
CPU `hist`, до 500 деревьев, early stopping 40, `learning_rate=0.05`.
Выбор обоих моделей — по NDCG@5 на validation с метками кликов.
Основная метрика — среднее NDCG@5 по запросам, дополнительно NDCG@3.
Запрос без кликов получает 0, как в XGBoost `ndcg@5-`; число таких запросов отражено в JSON.
Группы с одинаковыми метками сохраняются: они не создают полезных ранжирующих пар,
их количество также отражено в отчёте.

Oracle NDCG@5 использует **линейный gain по вероятности интереса** и отвечает на отдельный
вопрос: насколько модель восстановила скрытый порядок симулятора. На него не настраиваем
модель. Правила сравниваются с исходной сортировкой бэкенда: вес, свежая дата, ID.
95% CI разницы XGB и бейзлайна считается парным bootstrap по клиентам (1000 повторов).

Измеренные результаты: [reports/metrics.md](reports/metrics.md).
В исходном эксперименте XGBoost заметно лучше правил, но его небольшое преимущество
над логрегом по кликам не подтверждено доверительными интервалами: на каждом seed
95% CI разницы включает ноль. На аддитивном сценарии логрег лучше.
Это сравнение синтетических гипотез, а не гарантия превосходства выбранной модели.

Полные параметры, размеры выборок и метрики: [reports/experiment.json](reports/experiment.json).

## Подбор гиперпараметров

Текущая модель — `feed-xgb-0.2.0-seed-42`, выбранная по validation после расширенного
поиска. Исходные веса и бейзлайн сохранены в `models/initial/`.

Проверены 33 конфигурации: глубина 1–6, скорость обучения 0.025–0.15,
регуляризация L1/L2, минимальный вес листа, доли строк/признаков и стратегии пар
`mean`/`topk`. Число деревьев — до 1000 с early stopping. Шесть лучших конфигураций
и исходная проверены на validation seed 43/44; окончательный выбор — по среднему
validation NDCG@5 трёх seed. Настройки и выбор зафиксированы **до генерации** новой
проверочной выборки seed 20261024 (4000 новых клиентов, 12000 запросов).
Симулятор, признаки, старые train-данные и определение основной метрики не менялись.

[Отчёт подбора](reports/tuning.md) содержит параметры, результат на новой выборке и CI.
В нём также показана диагностическая метрика только по запросам с кликами;
она не заменяет основную метрику и не используется для выбора параметров.
Прирост относительно логрега подтверждается на новой синтетике; относительно
первого XGBoost CI разницы едва включает ноль. Сортировка по скрытой вероятности
симулятора — дополнительный диагностический ориентир, не доступный рабочей модели.

```bash
# Воспроизвести уже зафиксированную выбранную модель, проверить точное совпадение
# предсказаний и метрики; основные артефакты не перезаписываются:
./run.sh python -m ml.synth.tune --reproduce
```

Первичный поиск запускался командой `./run.sh python -m ml.synth.tune`.
Повторный новый поиск этим протоколом заблокирован после просмотра новой выборки;
для следующего исследования нужен новый протокол и ещё одна независимая выборка.
`--reproduce` воспроизводит существующее решение без нового выбора по результатам.
Запуск старого `experiment` заново опубликует исходную модель вместо настроенной.

Параметры ранжирования сверены с [документацией XGBoost](https://xgboost.readthedocs.io/en/stable/tutorials/learning_to_rank.html).

## Рабочий вызов

```python
from ml import rank_feed, rank_products, warmup

warmup()  # один раз при старте сервиса, до приёма запросов
response = rank_feed(payload)
# {"model_version": "...", "ranking": [{"id": "...", "score": 0.7, "reasons": []}, ...]}
```

В окружение вызывающего процесса нужно установить зависимости из
`ml/dependencies-runtime.txt` и обеспечить доступ к пакету `ml/` вместе с `ml/models/`.
Для используемого sklearn-интерфейса XGBoost нужен также scikit-learn;
все три прямые зависимости указаны в runtime-файле. Ранжирование выполняется в процессе, без сети и БД. Веса загружаются при первом вызове
и кешируются. **До приёма запросов обязательно вызвать `ml.warmup()`**: на этой машине импорт
библиотек и первый вызов занимают около 2.2 с, то есть превышают бюджет 1 с.
После прогрева p95 для 15 кандидатов — около 0.19 мс. Время старта зависит от окружения;
готовность сервиса следует объявлять после успешного `warmup()`.
`rank_products` и импорт `ml` не требуют загрузки XGBoost.
Замеры холодного старта и 1000 прогретых вызовов с 15 кандидатами: `reports/latency.json`.

Для контракта `score ∈ [0, 1]` используем сигмоиду исходного ранжирующего балла.
Это **не вероятность клика**, и сравнивать такие числа между разными запросами не следует.
Сортировка выполняется по исходному баллу, при равенстве — по ID. `reasons=[]` позволяет
бэкенду использовать свои объяснения. Ошибки загрузки или предсказания не маскируются:
вызывающая сторона должна применять предусмотренный контрактом возврат к правилам.

Подключение к `GET /feed`, установка зависимостей в backend/Docker и управление таймаутом
относятся к интеграции бэкенда. В этой работе файлы вне `ml` не меняются.
`models/logistic.json` содержит полный бейзлайн без pickle; основной артефакт —
`models/feed_ranker.ubj`, метаданные — `models/metadata.json`.

## Ограничения

Только синтетические клиенты и клики; данные БКИ, банка и внешние датасеты не используются.
Модель восстанавливает заданные поведенческие гипотезы. Результат не доказывает рост CTR
реальных пользователей. Каталог — 28 фиксированных новостей; проверка идёт на новых
клиентах с тем же каталогом, а не на новых текстах. Модель не анализирует текст новости.
Пропущенная выручка и нулевой рост не различаются в исходном наборе признаков.
Симулятор не моделирует смещение кликов по позиции и не воспроизводит реальную воронку.
Добавлять взаимодействия специально ради победы XGBoost после просмотра теста нельзя.
Дополнительный аддитивный сценарий показывает зависимость преимущества от гипотез.
